Every protocol failure gets an entry, logged in the same session it's noticed (see "Self-Improvement Loop" in SKILL.md). Format per entry: **date • bug • tripwire • what happened • patch produced.** An entry with no patch line is itself a violation.

## 2026-07-11 — deactivated account STILL receiving commissary catalog emails (repeat of a "fixed" bug)

- **Bug in one line:** Divya's deactivated account (is_active=false since 2026-04-21) kept receiving "Commissary pack change" emails on 2026-07-11 — three months after deactivation, and eight days after PR #2066 ("deactivated accounts stop receiving notifications", merged to main 2026-07-03) declared this exact bug fixed.
- **Tripwire:** *"The fix bounced because it covered one scenario of a correct cause"* — a step-5 scenario-mapping miss, committed by the PRIOR run of this protocol. #2066's diagnosis was CORRECT (recipient lookups select by role from `user_restaurants` and never check `profiles.is_active`). Its fix guarded the shared dispatcher (`producer.ts` `resolveRecipients` → `dropDeactivatedRecipients`) and the queue worker (`email-worker.ts`), and its own commit message claimed: *"This is the single front door every notification passes through, so it covers ALL alert types and ALL channels."* **That claim was never verified.** `lib/sale-items/distribution-sync.ts` builds its OWN recipient list (`user_restaurants` + `profiles`, no is_active) and calls `sendEmail()` DIRECTLY — bypassing both the guarded dispatcher and the guarded queue. A second front door, unaudited.
- **What the protocol said vs what happened:** step 5 requires the fix to cover the confirmed cause *everywhere it can bite*, not just the slice reproduced. The cause was "recipient resolution ignores is_active" — a whole CLASS spanning every recipient-resolving sender. The fix mapped ONE sender family (queued/producer-routed alerts) and asserted totality instead of enumerating the senders. A 30-second sweep (`grep -rn "sendEmail(" lib app`) lists all 10 direct callers and would have surfaced `distribution-sync.ts` immediately. It was never run.
- **Excuse used (implicit, and written into the commit message as fact):** *"producer.ts is the single chokepoint every notification passes through."* An architectural belief about a chokepoint is a HYPOTHESIS about call-sites; it is killed or confirmed by enumerating callers, not by asserting it. Same failure family as "the smoking gun in the code is obvious" — an unverified structural claim promoted to a fact.
- **Cost:** the user re-reported a bug she had already paid for once, and reasonably asked "why is this still live — we debugged this before?" Repeat-bug reports are the most expensive kind: they spend trust, not just time.
- **Patch produced:** new red flag + rationalization row — when a fix is a CHOKEPOINT/single-front-door fix, the chokepoint claim MUST be proven by enumerating every caller of the underlying primitive (the send/write/dispatch function) and showing each one routes through it; senders that call the primitive directly are un-guarded side doors. Enumerate, don't assert. Also added to step 5's always-in-the-map list.
